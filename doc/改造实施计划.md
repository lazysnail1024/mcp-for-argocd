# `argocd-mcp-plus` (`0.9.1`) 改造实施计划

## 一、 改造目标与总体原则

本次改造基于当前仓库现有 TypeScript 代码库原地演进，目标是消除底层请求构造与大响应稳定性缺陷，补齐上下文噪音裁剪与细粒度工具门控能力，并将协议底座升级至支持 MCP `2026-07-28` 的无状态架构，同时保持对存量主流 MCP 客户端与启动参数的兼容。

整体遵循四项工程原则：

1. **优先复用存量成熟代码，不重复造轮子**：完整保留当前仓库的 TypeScript 工具链、基于官方 `swagger.json` 生成的强类型定义、网络监听安全校验中间件（回环默认绑定、`Host`/`Origin` 校验、常量时间 Bearer 鉴权）以及绑定域名的多实例 `TokenRegistry`，不做跨语言重写，也不在进程内自建网关级 OAuth 授权服务或异步任务轮询引擎。
2. **允许必要的破坏性清理，精准改掉不合理设计**：移除无法支持多副本负载均衡的旧式双端点 `sse` 有状态传输与内存会话字典；改变过去默认敞开全部高危写工具的做法，默认仅启用 `core,diagnostics` 只读工具集；保留现有目录主干，对单体 `server.ts` 做清晰的职责拆分。
3. **规避上游官方命名，版本从 `0.9.1` 起步**：将包名、MCP 服务标识、Kubernetes 部署资源名及默认容器镜像名统一设定为 **`argocd-mcp-plus`**，版本号定为 **`0.9.1`**，默认交付镜像为 **`argocd-mcp-plus:0.9.1`**，避免与上游 `argocd-mcp` 及 `argoproj-labs/mcp-for-argocd` 产生混淆或标签覆盖。
4. **交付精简 `-slim` 镜像并在本机 `kind` 集群闭环验收**：沿用上游 `main` 分支的多阶段 `node:*-slim` 跨架构构建模式（升级至受支持的 `node:22-slim` 并清理运行期冗余源码层），最终在本机 `kind` 集群以双副本无状态形态完成端到端实测验收。

### 2.2 现状代码中存在的不合理设计与具体缺陷

1. **REST 路径直接拼接存在路径穿越风险**：`src/argocd/client.ts` 中 14 处请求路径直接采用模板字符串拼接（如 `` `/api/v1/applications/${applicationName}` ``），未校验路径段合法性也未执行单段 URL 编码。一旦模型受外部文本诱导传入 `../clusters/xxx` 或 `../repositories/xxx`，会携带服务端出站 Token 跨路由访问甚至删除其他管理资源。
2. **`ARGOCD_BASE_URL` 包含子路径时被静默截断**：`src/argocd/http.ts` 的 `absUrl()` 调用 `new URL('/api/v1/...', this.baseUrl)`。由于相对路径以 `/` 开头，当 Argo CD 部署在反向代理子路径（如 `https://devops.example.com/argocd`）下时，标准 `URL` 解析会直接丢弃 `/argocd` 前缀导致请求 404。
3. **未校验下游 HTTP 非 2xx 状态码**：`src/argocd/http.ts` 在 `fetch` 返回后未检查 `response.ok` 直接调用 `response.json()`。当下游返回 401/403/404/500 时，若返回体是非 JSON 网关错误页会抛出难以理解的 `SyntaxError`，若返回体是错误 JSON 则会被包装成 `isError: false` 的正常结果误导模型。
4. **`list_applications` 的 `search` 参数无效**：`src/argocd/client.ts` 将 `{ search }` 作为查询参数直接传给 `/api/v1/applications`，但 Argo CD 后端接口并不识别 `search` 参数，实际返回的是未过滤的全量应用列表。
5. **默认全量暴露高危写操作且缺乏工具风险注解**：`src/server/server.ts` 在默认配置下同时开启应用创建、覆盖更新、级联删除、允许 `prune: true` 的同步以及任意资源 Action，仅提供一刀切的 `MCP_READ_ONLY` 布尔开关，且所有工具均未声明 `readOnlyHint`、`destructiveHint`、`idempotentHint` 元数据。
6. **大对象无界并发拉取与噪音元数据膨胀**：
   - `src/server/server.ts` 中的 `get_resources` 在未传 `resourceRefs` 时会自动拉取整棵资源树（且漏传了 `applicationNamespace`），随后通过 `Promise.all` 并发请求应用下**每一个节点**的完整清单，包含冗长的 `metadata.managedFields` 与 `kubectl.kubernetes.io/last-applied-configuration`，在大应用下极易超出上下文窗口或反向代理行缓冲上限。
   - 在机密信息已规范收敛于 Kubernetes `Secret` 的前提下，Argo CD API Server 的 `GetResource` 与 `ManagedResources` 接口默认已通过 `HideSecretData` 将标准 `v1/Secret` 的值掩码为 `********`（无需对 `ConfigMap` 等普通配置做额外正则扫描）；仅需对显式带有 `argocd.argoproj.io/show-secret-value: "true"` 豁免注解的 `Secret` 增加出口兜底掩码，防止明文值意外进入模型上下文。
   - `get_application_workload_logs` 将 `container` 参数写死为必填字符串（与其描述中的可选语义矛盾，导致单容器 Pod 未传容器名时报错），且缺少单次响应字节上限与服务端关键字过滤。
7. **`ApplicationSchema` 必填约束过严**：`src/shared/models/schema.ts` 要求 `spec.syncPolicy`（含 `retry` 与 `syncOptions`）必填，导致常规精简版 Application 定义无法通过入参校验。
8. **默认有状态会话映射与类继承耦合**：`src/server/transport.ts` 默认在进程内存中维护 `httpTransports[sessionId]` 和 `sse` 会话表，多副本部署在无粘性会话下必然触发会话丢失报错；`Server` 直接继承 `McpServer` 并在构造器内耦合了默认凭据与全量工具注册，不利于按请求隔离出站凭据和模块化管理。

### 3.2 `--stateless` 兼容设计与移除 `sse` 后的客户端边界

1. **CLI 启动参数 `--stateless` 的平滑兼容**：
   - 由于 `src/cmd/cmd.ts` 开启了 `yargs.strict()` 严格参数校验（未知参数会直接导致启动退出），不能简单删除 `--stateless` 定义，否则存量脚本或 Kubernetes Deployment 中已配置的 `args: ["http", "--stateless"]` 会启动失败。
   - 改造后在 `http` 子命令中保留 `.option('stateless', { type: 'boolean', default: true })`：无论启动命令传 `http` 还是 `http --stateless`，均合法解析并进入唯一的无状态处理链路；若显式传入 `--no-stateless`（`stateless === false`），则在启动日志输出告警提示有状态内存会话已废弃，仍按无状态模式安全运行。
2. **协议层无状态（`legacy: 'stateless'`）对新旧客户端的具体处理机制**：
   - **现代 `2026-07-28` 客户端**：直接通过 `POST /mcp` 发送携带 `_meta` 的 `server/discover`、`tools/list`、`tools/call` 请求，服务端按单次请求处理完毕即释放；收到空的 `subscriptions/listen` 请求时确认后立即闭合响应流。
   - **存量 `2025-03-26` ~ `2025-11-25` Streamable HTTP 客户端**：
     - 握手阶段客户端发送 `POST /mcp` (`initialize`)，服务端通过无状态 Transport（`sessionIdGenerator: undefined`）正常返回 `InitializeResult`，响应头**不签发 `Mcp-Session-Id`**；客户端随后发送的 `notifications/initialized` 返回 `202 Accepted`。
     - 若部分客户端或前置网关在后续 `POST /mcp` 请求中仍附带了旧的或随机的 `Mcp-Session-Id` 头，服务端直接忽略该头而非报 `400 Invalid session ID`，确保多副本轮询零报错。
     - 当存量客户端握手后尝试发起 `GET /mcp` 建立独立长连接推送流，或退出时发起 `DELETE /mcp` 注销会话时，服务端按 MCP Streamable HTTP 无状态规范统一返回 `405 Method Not Allowed`（附 `Allow: POST` 头），客户端 SDK 收到 `405` 后会自动静默回退为纯 `POST /mcp` 请求响应模式（同时开启 `enableJsonResponse: true` 兼容纯 JSON 解析客户端）。
3. **移除 `sse` 子命令后的客户端覆盖边界**：
   - **`stdio` 本地客户端（100% 兼容）**：Cursor、VS Code、Claude Desktop、Claude Code 等本地子进程模式不受任何影响，同时兼容旧握手与 `2026-07-28`。
   - **连接 `/mcp` 的远程客户端（100% 兼容）**：主流 IDE、Agent 框架及各语言 SDK 均已支持 `/mcp` 端点，在上述无状态双代际机制下无缝工作。
   - **仅支持早期 `2024-11-05` 双端点 `GET /sse` + `POST /messages` 的遗留客户端**：此类客户端强依赖长连接绑定单实例内存 `sessionId`，接入时需将地址从 `/sse`（`type: "sse"`）调整为 `/mcp`（`type: "http"` / `streamable-http`）；如极端情况下确有无法改配的单实例遗留系统，可按需独立挂载官方冻结过渡包 `@modelcontextprotocol/server-legacy`。

## 四、 核心模块详细设计

### 4.1 双代际无状态传输与网关路由头校验（`src/server/`）

1. **无状态 HTTP 与 Stdio 统一组装**：
   - HTTP 监听沿用 Express 严格顺序：先注册免鉴权的 `GET /healthz`，再挂载 `applyListenerSecurity(app, security)`，随后经过 `headerGuard` 进入 SDK v2 无状态 `/mcp` 处理器。
   - 默认配置 `legacy: 'stateless'` 与 `enableJsonResponse: true`；支持通过 `--legacy-mode=stateless|reject`（或环境变量 `MCP_LEGACY_MODE`）控制是否拒绝旧版握手请求。
   - 由于工具集在进程启动期静态确定、不存在运行期工具动态增删，当客户端发起空的 `subscriptions/listen` 订阅流时，服务端确认后立即主动闭合流，避免空闲连接常驻泄漏。
2. **能力发现引导与缓存提示**：
   - 在 `McpServer` 中配置 `instructions`，明确指示模型排查应用异常时优先调用 `diagnose_application` 获取非健康节点与事件摘要、调用 `diff_application` 查看配置偏差，避免无过滤拉取整棵资源树或长日志。
   - `tools/list` 按工具名称字典序固定排序，在现代协议响应中附带 `ttlMs: 3600000` 与 `cacheScope: 'public'`，稳定客户端缓存与模型提示词缓存；涉及请求级凭据的数据调用统一标记私有作用域。
3. **可路由请求头与防协议失步校验（`headerGuard.ts`）**：
   - 在非敏感路由参数（`argocdBaseUrl`、`applicationName`、`project`）上标注 `x-mcp-header`（严禁在任何密钥相关字段上标注，防止凭据进入网关访问日志）。
   - 当入站请求携带 `Mcp-Method`、`Mcp-Name` 或 `Mcp-Param-*` 头时，服务端先处理 `=?base64?...?=` 编码解码与空串边界，再与 JSON-RPC 请求体中的 `method`、`params.name` 及对应参数严格比对；任何不一致立即返回 `400 Bad Request`（错误码 `-32020`），防止攻击者伪造外层 Header 绕过前置网关规则。未携带上述专属头的 `2025-xx` 请求在 `stateless` 兼容模式下正常放行至旧版分支。
4. **单请求凭据隔离与链路追踪透传**：
   - 将请求头 `x-argocd-base-url` 与 `x-argocd-api-token` 的解析限定在单次请求上下文中，严禁写入跨请求共享实例属性；在 `TokenRegistry` 中按文件 `mtime` 增量检测更新，实现 Secret 轮转热加载。
   - 提取入站 `X-MCP-Caller` 记入 `pino` 单行 JSON 审计日志（记录调用方、工具名、目标实例、应用名、耗时与是否报错，绝不记录 Token）；若请求 `_meta.traceparent` 存在，则在调用 Argo CD API 时原样透传该请求头。

### 4.2 下游请求构造加固与报错自愈转换（`src/argocd/`）

1. **受控 URL 构造器（`url.ts`）**：
   - 将 `baseUrl` 规范化为末尾带 `/` 的基础路径，拼接 API 相对路径时剥离前导 `/`（例如 `api/v1/applications`），确保 `https://host/argocd` 等子路径部署完整保留前缀。
   - 提供统一的 `encodePathSegment(value, fieldName)`：强制校验 `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,252}$`，显式拒绝 `.`、`..`、`/`、`\`、`%` 及空白字符，再执行 `encodeURIComponent`。`client.ts` 中所有 `applicationName`、`projectName`、`podName` 均必须通过该函数编码后拼入路径。
2. **非 2xx 异常拦截与面向 Agent 的错误改写（`errors.ts`）**：
   - 在 `HttpClient.request` 与 `requestStream` 中统一检查 `!response.ok`，兼容解析 JSON 错误体与纯文本网关报错，抛出包含 HTTP 状态码与下游信息的 `ArgoCDApiError`。
   - 在工具出口将异常转换为指向当前已注册工具的可恢复指引（返回 `isError: true`，不出具要求人工敲命令行登录的无效提示）：
     - `404` -> 提示未找到目标资源，引导先调用 `list_applications(search=...)` 或 `list_projects` 核对准确名称与 `applicationNamespace`。
     - `401 / 403` -> 明确提示下游凭据失效或超出当前账号 RBAC 项目权限，引导检查目标 `argocdBaseUrl` 或缩小查询项目范围。
     - `超出 64KB 响应熔断` -> 提示改用 `diagnose_application`、`diff_application`，或传入 `kind`、`name`、`tailLines`、`grep` 缩小返回体积。
3. **私有 CA 证书支持**：
   - 统一依托 Node.js 原生 `NODE_EXTRA_CA_CERTS` 环境变量加载自签发或企业内部根证书，在容器部署清单与文档中提供标准挂载示例，不再引导用户关闭全局 TLS 校验（`NODE_TLS_REJECT_UNAUTHORIZED=0`）。

### 4.3 模块化工具集与高信噪比排障工具（`src/toolsets/` & `src/governance/`）

1. **工具集划分与默认门控**：
   - `--toolsets`（或 `MCP_TOOLSETS`）**默认值为 `core,diagnostics`**，支持按需组合 `core`、`diagnostics`、`ops`、`admin` 或 `all`；支持 `--tools`（或 `MCP_TOOLS`）按单工具名称精确白名单过滤。
   - 保留 `MCP_READ_ONLY=true` 最高优先级保护：一旦开启，无论 `--toolsets` 如何设置均强制剔除 `ops` 与 `admin` 写工具集。
   - 为每个工具准确声明 `ToolAnnotations`（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint: false`）。
2. **各工具集包含工具与改造点**：
   - **`core`（默认开启，7 个只读工具）**：
     - `list_clusters`：列出已注册集群。
     - `list_projects`（新增）：调用 `GET /api/v1/projects`，返回项目名称、描述、允许的源仓库与目标集群摘要。
     - `get_appproject`：获取指定项目详情（经噪音裁剪）。
     - `list_applications`（修复增强）：支持 `project`、`healthStatus`、`syncStatus`、`appNamespace` 过滤；在服务端内存完成不区分大小写的 `search` 名称子串匹配后再执行 `offset`/`limit` 分页（默认 `limit: 50`）。
     - `get_application`：支持可选 `refresh: 'normal' | 'hard'` 参数，返回剥离冗余历史与机器噪音后的应用详情。
     - `diagnose_application`（新增聚合诊断）：服务端并发拉取应用详情、资源树与事件列表，在内存中直接过滤掉全部 `Synced` 且 `Healthy` 的正常节点，仅提炼异常/失步子资源、最近一次 `operationState` 报错摘要及 `Warning` 事件；若检测到 `Rollout` 处于暂停态，自动附带渐进式发布暂停说明，避免模型误判为故障崩溃。
     - `diff_application`（新增结构化差异）：基于受管资源接口在服务端解析对比 `normalizedLiveState`/`liveState` 与 `targetState`，剥离无关元数据后仅输出存在偏差的资源标识与变更字段摘要，替代直接倾倒大段原始 JSON 字符串。
   - **`diagnostics`（默认开启，7 个只读深度排障工具）**：
     - `get_application_resource_tree`：新增 `detailLevel: 'summary' | 'detailed'`（默认 `'summary'` 返回按资源类型聚合的健康统计与异常节点分支，`'detailed'` 返回清洗后的完整节点列表）。
     - `get_application_managed_resources`：支持按 `kind`/`namespace`/`name`/`group`/`version` 过滤并执行噪音字段清洗。
     - `get_resources`：修复漏传 `applicationNamespace` 的缺陷；当未传 `resourceRefs` 且应用资源节点数超过安全上限（20 个）时拒绝全量并发拉取，引导传入具体 `resourceRefs` 或先用 `diagnose_application` 定位异常对象。
     - `get_application_events`、`get_resource_events`、`get_resource_actions`：保持语义不变并接入统一路径编码与输出清洗。
     - `get_application_workload_logs`：将 `container` 改为可选参数，支持可配 `tailLines`（默认 100，上限 500）与服务端 `grep` 过滤，单次返回硬限 `32KB`。
   - **`ops`（默认关闭，2 个受控运维工具）**：
     - `sync_application`：新增 `resources` 数组支持按 `group/kind/name/namespace` 局部同步；服务端默认强制锁死 `prune: false`（仅当环境变量 `MCP_ALLOW_PRUNE=true` 显式放开时才允许传入 `prune: true`）。Argo CD 的 `/sync` 接口本身为异步触发并立即返回 `operationState`，无需额外封装后台任务状态机，后续直接通过 `diagnose_application` 或 `get_application` 即可查看同步收敛进度。
     - `run_resource_action`：支持通过 `MCP_ALLOWED_RESOURCE_ACTIONS` 配置允许执行的动作白名单（如仅放行 `restart`）。
   - **`admin`（默认关闭，3 个应用生命周期工具）**：
     - `create_application`、`update_application`（放宽 `ApplicationSchema` 中 `syncPolicy` 的非必填约束）、`delete_application`。

### 4.4 输出噪音清洗、64KB 熔断与双代际写确认护栏（`src/governance/`）

1. **统一输出噪音清洗与 `Secret` 兜底掩码（`sanitizer.ts`）**：
   - 递归剔除 `metadata.managedFields` 与 `metadata.annotations['kubectl.kubernetes.io/last-applied-configuration']`，消除 Kubernetes 机器元数据噪音。
   - 鉴于机密信息已统一存放在 `Secret` 中，不对 `ConfigMap`、环境变量或 Helm 参数做额外键名正则匹配处理（避免误伤正常业务配置字段）；仅对 `kind === 'Secret'` 的对象保留 `data` / `stringData` 兜底掩码为 `"[REDACTED]"`，防止带有 `show-secret-value: "true"` 注解的 `Secret` 明文流出。
2. **64KB 字节硬熔断（`byteBreaker.ts`）**：
   - 全局默认响应上限 `MCP_MAX_RESPONSE_BYTES = 65536`（64KB）；序列化结果超限时绝不截断输出半截损坏文本，直接交由错误转换器返回带过滤建议的 `isError: true` 结构化提示。
3. **项目与命名空间作用域围栏（`scopeFence.ts`）**：
   - 支持配置 `MCP_ALLOWED_PROJECTS`（允许访问的 Project 白名单）与 `MCP_DENIED_NAMESPACES`（禁止访问的目标命名空间黑名单），在列表输出过滤与单应用读写调用前双向强制执行。
4. **兼顾双代际客户端的写操作确认护栏（`mrtrGate.ts`）**：
   - 复用 `@modelcontextprotocol/server` 内置的 `createRequestStateCodec`（HMAC-SHA256 签名，绑定工具名、目标应用、参数摘要、调用方标识与 300 秒有效期，密钥取自 `MCP_REQUEST_STATE_SECRET` 或启动期随机密钥）。
   - 严格依据请求实际生效的协议代际分流（不直接对客户端原始版本字符串做字典序比较）：
     - **当客户端运行在 `2026-07-28` 协议且支持表单征询时**：执行 `delete_application`、开启 `prune: true` 的 `sync_application` 等高风险操作，首轮返回 `inputRequired`（`resultType: "input_required"`）及签名 `requestState` 挂起确认；次轮在任意副本验签通过后执行。
     - **当存量客户端运行在 `2025-xx` 无状态兼容路径时**：因无反向征询通道，`delete_application` 要求显式传入与目标一致的 `confirmApplicationName` 参数防误删，`sync_application` 则依靠服务端硬锁 `prune: false` 保障安全。
   - 所有工具入参 Schema 均禁止使用协议层保留字段名 `inputResponses` 与 `requestState`，防止旧代际请求参数被协议层剥离。

## 五、 容器镜像方案（基于官方 `main` 的 `-slim` 多阶段演进）

经核查上游 `main` 分支 `Dockerfile`，官方采用 `node:20-slim` 多阶段构建（并在编译阶段通过 `FROM --platform=$BUILDPLATFORM` 在宿主机原生架构运行 `tsup/esbuild` 以规避跨架构 QEMU 崩溃，最终以 `USER 1000` 运行 `ENTRYPOINT ["node", "dist/index.js"]` + `CMD ["http"]`）。

在此基础上，保持官方 `-slim` 精简路线并修复原有 `Dockerfile` 将全量源码带入运行层的问题：

1. **升级基础镜像至 `node:22-slim`**：同属官方 Debian `-slim` 最小化 Node 镜像体系，满足 `@modelcontextprotocol/server` v2 的 Node `>=20` 要求，同时避开已进入生命周期尾声的 Node 20。
2. **新增 `.dockerignore` 并分离干净的运行阶段**：
   - `.dockerignore` 排除 `node_modules`、`dist`、`.git`、`doc`、`*.test.ts` 等无关文件。
   - `prod-deps` 与 `build` 阶段先仅拷贝 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml` 执行 `pnpm install --frozen-lockfile` 以充分利用镜像层缓存；`build` 阶段继续保留 `--platform=$BUILDPLATFORM` 原生编译。
   - 最终运行阶段直接基于干净的 `FROM node:22-slim`（不再继承含全量源码与 `corepack` 缓存的中间 `base` 层），仅拷入 `package.json`、`prod-deps` 的 `node_modules` 与 `build` 产出的 `dist`，保持 `EXPOSE 3000`、`USER 1000`、`ENTRYPOINT ["node", "dist/index.js"]`、`CMD ["http"]`。
3. **默认构建标识**：`argocd-mcp-plus:0.9.1`（在 `Makefile` 中提供 `IMAGE_NAME ?= argocd-mcp-plus`、`IMAGE_TAG ?= 0.9.1` 参数化构建与 `kind` 加载目标）。

### 6.3 本机 `kind` 集群 E2E 测试架构与用例设计

#### 1. 集群拓扑与环境准备（无损复用宿主机 `kind` 集群）

- **控制面检测与复用**：自动化脚本先检查宿主机 `kind` 集群（`kubectl config use-context kind-kind`）中的 `argocd` 命名空间：
  - 若集群已安装 Argo CD 且 `argocd-server` 正常就绪，直接复用现有控制面，仅创建独立的 E2E 测试专用 `AppProject`（`mcp-e2e-project`）、独立业务命名空间（`mcp-e2e-ok`、`mcp-e2e-broken`、`mcp-e2e-denied`）及测试专用 RBAC Token，不改动集群内任何既有应用；
  - 若集群尚未安装 Argo CD，则在 `argocd` 命名空间自动安装官方稳定版核心清单并等待就绪。
- **被测服务部署形态（`deploy/kind/`，独立命名空间 `mcp-e2e-system`）**：
  - 通过 `kind load docker-image argocd-mcp-plus:0.9.1 --name kind` 导入本地构建镜像，设置 `imagePullPolicy: Never` 确保 100% 运行本地待验收镜像。
  - 部署 **`replicas: 2` 的双副本 `Deployment`（`argocd-mcp-plus`）+ ClusterIP `Service`**，容器启动命令显式配置 `["http", "--stateless", "--bind-address", "0.0.0.0"]`：
    - 挂载包含 `MCP_AUTH_TOKEN` 与共享 `MCP_REQUEST_STATE_SECRET` 的 Secret（用于验证 Pod A 签发的审批签名落到 Pod B 上能跨副本验签）；
    - 将 Argo CD 的服务端 TLS 根证书挂载至容器内并通过 **`NODE_EXTRA_CA_CERTS`** 启用严格证书校验，集群内直连 `https://argocd-server.argocd.svc.cluster.local`（全程禁止配置 `NODE_TLS_REJECT_UNAUTHORIZED=0`）；
    - 挂载 `ARGOCD_TOKEN_REGISTRY_PATH` Secret 卷用于测试多实例域名绑定与文件热重载。

#### 2. 真实 GitOps 靶标应用构造（`deploy/kind/fixtures/`）

为使全部只读诊断与受控写工具在真实 Argo CD 上产生确定性可断言结果，在集群内预置两套靶标 Application：

- **靶标一：`e2e-healthy-app`（健康基线应用）**
  - 部署于 `mcp-e2e-ok` 命名空间，包含全部处于 `Synced` + `Healthy` 状态的 `Deployment`、`Service` 与普通 `ConfigMap`（含常规配置项如 `LOG_LEVEL=info`、`MAX_TOKENS=4096`，用于验证业务配置字段原样保留且 `managedFields` / `last-applied-configuration` 被干净剥离）。
- **靶标二：`e2e-broken-app`（综合异常、配置漂移与 Secret 验证靶标）**
  - 部署于 `mcp-e2e-broken` 命名空间，组合构造 4 类真实集群状态：
    1. **正常子资源**：1 个健康的 `Service`（用于验证 `diagnose_application` 会自动剔除正常节点）；
    2. **故障工作负载与事件/日志源**：1 个正常输出日志的轻量 `Pod/Deployment`（供无 `container` 参数日志拉取与 `grep` 过滤测试）+ 1 个使用无效镜像标签触发 `ImagePullBackOff` 的异常 `Deployment`（使应用整体处于 `Degraded` 并产生真实 Kubernetes `Warning` 事件）；
    3. **实态配置漂移（OutOfSync）**：在同步完成后通过 `kubectl patch` 修改集群内目标 `ConfigMap` 的键值，制造真实的 `liveState` 与 Git 期望 `targetState` 偏差（供 `diff_application`、局部 `sync_application` 验证）；
    4. **双形态 `Secret`**：1 个标准 `v1/Secret` 与 1 个带有 `argocd.argoproj.io/show-secret-value: "true"` 注解的 `v1/Secret`（供验证出口兜底掩码 `"[REDACTED]"`）。
